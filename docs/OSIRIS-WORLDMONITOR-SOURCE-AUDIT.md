# Osiris-Lab / WorldMonitor source audit

**Verification date:** 2026-10-24  
**Scope:** source candidates visible in the local Osiris-Lab and WorldMonitor checkouts, compared with Odin's existing [`DATA_SOURCES.md`](../DATA_SOURCES.md). This is an audit, not a blanket approval to reuse either project's data or code.

## Rules for interpreting the projects

- Osiris-Lab's root `LICENSE` is MIT, which licenses its code, not the independent datasets, camera images, video streams, news articles, or API services it calls. Its `package.json` does not declare a package license.
- The inspected WorldMonitor checkout has `"license": "AGPL-3.0-only"` in its root `package.json`; it has no `.git` directory or root license file in this checkout. Treat that as a code-reuse constraint, not as a licence for upstream data. WorldMonitor browser services call WorldMonitor RPC/bootstrap endpoints; those are project services, not proof that each upstream provider exposes a public API to Odin.
- Osiris-Lab's checkout has approximately 4,000 Git status entries. Its state is treated as read-only and potentially locally modified; conclusions below are from inspected files, not from a clean upstream revision. Neither project was modified.
- “Public API” below means a documented provider endpoint, not merely a URL used by another application. Unknown terms, quotas, or rights are recorded as unknown rather than inferred to be free.

## Repository findings that affect source selection

- Osiris's flight route actually calls OpenSky and `airplanes.live` endpoints despite comments mentioning other ADS-B services. `airplanes.live` terms, quota and reuse rights were not established here, so it is not proposed for Odin.
- Osiris's CCTV route combines periodic image snapshots, HLS streams, YouTube identifiers and external links. These must remain distinct media types. Its camera catalogue and status route do not establish that each underlying media URL is accessible, fresh, licensed, or continuously live.
- Osiris's inspected GDELT route creates synthetic random incident points if the real response is empty or fails. Odin must not treat those as observations.
- Osiris's inspected FIRMS route labels EONET volcano events as fires and assigns fixed brightness/FRP/confidence values. Odin must model EONET natural-event records with their actual category and metadata, never synthetic fire measurements.
- WorldMonitor's earthquake, EONET, wildfire and satellite frontend services use WorldMonitor RPC clients and hydrated/bootstrap data. The frontend code alone is not an independently callable upstream API, and its backend/configuration may carry deployment costs and provider-specific credentials.

## Recommendation and next steps

1. **Candidate for a separately scoped Odin integration: NOAA SWPC.** It adds space-weather data not present in Odin, has an official keyless JSON endpoint that passed a bounded live request, and has no published numeric quota found in the reviewed access guidance. Before implementation, inspect product schemas/attribution, cache conservatively, expose source timestamps and unknown/stale/error states, and test partial failures. Keep any key optional/server-side if NOAA changes access requirements.
2. **Defer EONET.** It is a potential complement to earthquakes/fires, but the live endpoint timed out and its events link to multiple underlying sources. Re-test with a single bounded call later; review data and media rights per source before display or redistribution.
3. **Do not duplicate existing coverage:** USGS earthquakes, NASA FIRMS, GDELT, ADS-B fallback, AIS, TomTom and multiple official CCTV packs already exist in Odin. Candidates from Osiris/WorldMonitor must show a concrete geographic/product gap to justify another connector.
4. **Resolve OpenSky permission separately.** Do not infer that the current integration is eligible for a deployed operational service. Obtain and record written permission, or make a later product decision about an eligible replacement. This audit preserves the existing connector and does not silently change behavior.
5. **Keep candidate registry metadata explicit:** provider; code licence versus data terms; access type; key location; quota; permitted use; attribution; last check; tested endpoint/result; and media/data freshness. Unknown fields should remain marked unknown and gate activation where they affect lawful use.

No new provider was integrated in this audit: the strongest additive candidate (SWPC) has a tested endpoint but lacks an implementation scope/UI decision in this request; EONET and GDELT failed bounded reachability checks here; other apparent sources are duplicates or have unresolved terms. No paid source was added, no service was installed, and neither Osiris-Lab nor WorldMonitor was changed.
